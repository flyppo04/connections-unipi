Il bug segnalato nel commento dentro handleGameInfo è reale: basterebbe aggiungere un controllo game.isExpired() prima di verificare state.hasFinished() per distinguere correttamente partita storica da partita in corso.


PlayerGamsestate.java

Nota su Thread-Safety
PlayerGameState non è thread-safe internamente (ArrayList non sincronizzate, campi primitivi non volatile). La sicurezza è garantita a livello superiore da ConcurrentHashMap in Game e dalla logica in GameManager.submitProposal() che usa la copia locale di currentGame. Tuttavia, se due worker thread gestissero lo stesso utente contemporaneamente, ci sarebbe una race condition su addCorrectGroup/addMistake → da verificare se CommandHandler ha protezioni a riguardo.


------------Client---------------
⚠️ Piccole criticità (minori)
1. Timeout fisso in readResponse
TIMEOUT_MS = 5000 è hard-coded. Se il server impiega più di 5s a rispondere (es. processamento pesante), il client va in timeout anche se il server poi risponde. Non è un problema critico per questo progetto, ma potresti alzarlo a 10s o renderlo configurabile.

2. partialMessage condiviso tra sendAndReceive
Il buffer partialMessage è un campo dell'istanza, quindi se ci sono residui da una risposta precedente (molto improbabile, ma possibile in caso di errori di parsing), potrebbero interferire con la successiva. Nella pratica con synchronized non succede, ma per robustezza potresti svuotarlo a inizio sendAndReceive.

3. Chiavi config diverse tra server e client
Client usa server.tcp.port, il server usa server.tcp.port. Ok, ma il client ha anche client.udp.port che il server non legge — il server riceve la porta UDP dal campo JSON udpPort nel login. Questo è corretto, ma assicurati che nel client.config la chiave sia documentata.

4. Nessun handling di disconnessione improvvisa del server
Se il server crasha durante una sessione, channel.read() torna -1 e lanci IOException("Connessione chiusa dal server"). Ottimo. Ma poi il client esce subito dal run(). Potresti offrire un'opzione "riconnetti", ma per un progetto didattico va bene così.

5. Case nelle parole proposte
In doSubmitProposal converti le parole a toUpperCase() prima di inviarle — ottimo, ma il server fa il confronto con equalsIgnoreCase. Funziona, ma se nel tuo stato locale currentWords sono già uppercase, quando rimuovi le parole trovate con currentWords.remove(w.getAsString()) stai confrontando uppercase con uppercase — coerente ✅. Perfetto.
